## 5. בדיקת release (שלב 3)

- **אין דרך להריץ profile או release על הסימולטור.** Flutter תומך במצבים האלה רק במכשיר iOS פיזי, ולא היה מכשיר מחובר. `flutter build ios --release --no-codesign` עבר (AOT, tree-shaking, Runner.app 27.2MB), כלומר אין כשל קומפילציה או tree-shaking.
- **סקירת ההבדלים בין release ל-debug (grep `kReleaseMode`, `kDebugMode`, `assert`, `compute`, `Isolate`):**
  - `ApiClient.baseUrl` ו-`apiOrigin`: ב-release ברירת המחדל היא `https://invoice.crm.tevel.space`, ו-`productionApiUri` דוחה http. אין שינוי התנהגות במעברים.
  - `compute(_decodeJsonBytes)`: פונקציה top-level, sendable. נבדק בפועל: ל-staging יש 732 לקוחות, כך שהנתיב מעל 50KB רץ בסריקה. נוספה הקשחת טיפוס (ממצא 9).
  - `Isolate.run(_toJpeg)` בהוצאות: ה-closure לוכד רק `Uint8List` ו-int, ולכן sendable.
  - `kDebugMode`: dev server (פורט 9999), ספירת PrimaryButton, מסך הדגמת סליקה. כולם כבויים ב-release ואינם נוגעים במעברים.
  - `assert`: רק שתי בדיקות טהורות, בלי תופעות לוואי.
  - **מה שבאמת שונה ב-release:** assertions של Navigator ושל build לא נבדקים. לכן כל מה שבסריקה (debug) היה "שגיאה" הופך ב-release למצב שבור שקט: מסך אפור, לחיצה מתה או layout חתוך. הסריקה ב-debug היא לכן הרשת הנכונה, והתיקונים שלמעלה הם בדיוק המקרים האלה.
- **סיכון שלא שונה (החלטת מוצר):** כשהאפליקציה עולה מה-cache, `auth_flow` מציג את הבית מיד ובודק מנוי ברקע (`_subscriptionGate(null)`). אם לעסק אין מנוי פעיל, הבדיקה עושה `pushAndRemoveUntil` למסך המנוי הנדרש, מאפסת את כל המחסנית גם אם המשתמש כבר התחיל פעולה, ואחרי X חוזרת ל-`resetToHome` וגיליון התוכניות נפתח שוב. ב-production, בעסק בלי מנוי Apple, למשתמש זה נראה כמו "קפיצה" מאמצע פעולה. ממליץ לבדוק אם לעסק של הבעלים ב-production יש מנוי פעיל. בסריקה ה-guard הקיים של ה-QA סוגר את מסכי התוכניות כמו X של משתמש.

**לא שוחזרה** קריסה בדיוק לפי התיאור ("מוסיף לקוח, חוזר, הכול קורס") ב-debug מול staging. הסיבות שנשארו: נתונים או מנוי של production, או התנהגות מכשיר אמיתי (מקלדת, ממצא 10). יומן התקלות (סעיף 3) נועד לסגור את הפער הזה מ-TestFlight.
